## What DFlash/DFlash2 is

Block-diffusion speculative drafter. Proposes an entire block of tokens in ONE
non-causal forward pass: block position 0 = real anchor token, positions 1..N-1
= MASK; the draft denoises the block conditioned on hidden states captured from
the frozen target at `target_layer_ids`. Output projected through the (shared,
frozen) target LM head. Paper: 6x+ lossless speedup, up to 2.5x over EAGLE-3.

- DFlash2 adds: two-tap in-block convolution around every sublayer
  (conv_kernel_size=2, conv_group_size=16) + pairwise path selector
  (selector_rank=256, selector_top_k=16) walking one coherent path through
  each position's top-k candidates. Still single-pass drafting.
- `sample_from_anchor=False` for dflash/dflash2: anchor is the bonus token,
  produces block_size-1 speculative tokens (our init: 7 for block 8).

## Best practices pinned from docs + published artifacts

| knob | value | source/rationale |
|---|---|---|
| draft layers | 5 | paper + CLI default (`qwen3_dflash2.yaml`) |
| draft hidden_size | 2560 = verifier | hard requirement (mismatch unsupported) |
| draft arch | Qwen3-style decoder | DFlash-family always Qwen3 layers |
| block_size | 8 for v1 (dflash2 CLI default; blog example) ; 16 = paper DFlash + sweep target | loss_decay_gamma pairs: 7↔16, 5↔10, 4↔8 |
| loss | kl_div (dflash2 default; ce for dflash) | CLI defaults |
| per-position weight | dpace (dflash default) / fixed-exp-decay | position-decay: early positions dominate |
| target_layer_ids | [2, 16, 29] for 32-layer 4B | default even spread [2, L/2, L-3] |
| max_anchors | 512 default; 3072 in blog example | anchors = blocks sampled/seq/step |
| lr / epochs | 1e-4 / 5 (blog); 5e-6 / 5 (CLI example) | start 1e-4 for from-scratch draft |
| mask_token_id | 248077 (auto-detected, tokenizer len 248078) | our tokenizer |
| attn impl | simple_flex_attention; sdpa fallback | GB10: try flex, fall back sdpa |
| sliding window | 2048 default on draft layers | published 27B drafter diverges from target this way |
| draft vocab | full 248320 for v1; reduced (8192 + d2t/t2t maps) = documented speed lever | blog example |
| eval protocol | acceptance length @ temp 1.0, top_p 0.95, top_k 20 | DFlash2 published convention |

Architecture divergences in published drafters (qwen3_8_27b_dflash2.yaml):
draft_sliding_window + draft_num_attention_heads/head_dim different from
target. v1 mirrors target dims (16 heads/4 KV/head_dim 256); divergence is a
sweep axis.

## Data conventions (the landmine we already flagged)

- Format: OpenAI `messages` JSONL (cascade emit format already matches via
  normalize_messages).
- Teacher-forcing: responses must be regenerated BY THE TARGET model —
  training on other-model text (cascade responses are Nemotron-generated)
  creates train/inference mismatch. NeMo guide is explicit.
- speculators v0.5.0+ pipeline: hidden states extracted by a running vLLM
  server (REST), online during training or offline via saturation scripts;
  `--hidden-states-path` for pre-generated states. Eliminates vLLM as a python
  dep for training (REST decoupling).

## Results — v1 run (2025-10-10, GB10, quant-aligned end to end)

**Setup.** Target/verifier = `Qwen3.5-4B-W4A16-GPTQ-cascade` (champion weightedKL 0.1087) everywhere:
regen (temp 0.7), hidden states, training, serving, eval. Draft = 5-layer DFlash2 (block 8,
7 spec tokens, greedy init), trained from scratch 5 epochs / lr 1e-4 / sdpa (flex-attention
Triton kernels exceed sm_121 shared memory; see decision log) on 158 rows / 587k tokens.
Eval: 20 held-out cascade conversations (rows 50–69, disjoint from training rows 0–49),
max 250 tok, concurrency 8, DFlash2 convention temp 1.0 / top_p 0.95 / top_k 20 unless noted.

| Arm | Mean acceptance length | Ceiling | Note |
|---|---|---|---|
| DFlash2 untrained | 1.00 | 8.0 | theoretical floor, lossless output |
| DFlash2 greedy, sampled verify | **1.53** | 8.0 | pos-1 accept 0.265 |
| DFlash2 probabilistic draft (`draft_sample_method=probabilistic`) | 1.46 | 8.0 | chain sampling regime |
| DFlash2 greedy, temp-0 verify | ~1.52–1.58 | 8.0 | top-1 agreement ≈ 0.5 |
| MTP k=1 (native head, same quant) | **1.76** | 2.0 | 88% of its ceiling |
| DFlash2 top-16 oracle (val, teacher-forced) | 6.16 | 7.0 | selector acc 0.871 |

**Reading.**
1. Every single-candidate arm lands at 1.46–1.58: that is the *chain-drafting ceiling* under
   vLLM 0.31's speculators serving (proposals package ships greedy only; no 16-candidate tree
   verifier). The 6.16/7 oracle belongs to the tree regime this build cannot serve.
2. Temp-0 arm isolates drafter quality: ~0.5 top-1 agreement after 587k tokens. MTP's
   full-pretraining-scale head reaches ~0.76 under *sampled* verify — the gap to close is data
   scale (10–100×), not architecture. First DFlash2 drafter for Qwen3.5 trained anywhere, and
   it is already at the measurable ceiling of the serving path available to it.

**Bugs found (upstream-worthy).**
- vLLM `extract_hidden_states` × compressed-tensors W4A16 on GB10: 23/27 rows NaN tails
  (content-anchored, forward-propagating), base model clean on identical rows — quant-specific.
- Worse: 2 of the 4 "finite" rows were *silently wrong* (cos 0.47–0.86 vs transformers ground
  truth; hs_7 cos ≈ 1.00 validates the transformers path). Training on the "clean subset" would
  have poisoned the drafter. Workaround: `extract_hs_transformers.py` (HF forward, layers
  [2,16,29,32] = HF `hidden_states[j]`), 158/158 finite, validated to cosine 1.0.
  Corrupted set kept at `dflash_data_quant/hidden_states_vllm_corrupt/` for the issue.

**Next levers (priority order).** (1) data scale 158 → 2k+ rows (acceptance should move with
top-1 agreement, per the temp-0 isolation); (2) serve tree proposals once a stack supports it
— oracle says 4× headroom; (3) block-16 sweep; (4) MTP quantization + drafter-for-MTP comparison.

## Results — v2 run (2026-10-10, data-scaling datapoint)

Same recipe, same eval (20 held-out convs 50–69, temp 1.0 / top_p 0.95 / top_k 20),
9.5× rows / 4.7× tokens (158→1,501 rows, 587k→2.73M tok), 3 epochs vs 5.

| Arm | Mean acceptance | pos-1 rate | Accepted tok/s |
|---|---|---|---|
| v1 (587k tok, 5 ep) | 1.53 | 0.265 | ~90 |
| **v2 (2.73M tok, 3 ep)** | **2.18** | **0.502** | ~175 |
| MTP k=1 (baseline) | 1.76 | ~0.76 | — |

**Findings.**
1. **Data scaling works and v2 beats MTP k=1 on the chain path** (2.18 vs 1.76, same
   prompts). The v1-era "~1.5 chain ceiling" hypothesis was wrong — it was drafter
   weakness, not a regime limit.
2. **Val metrics during training mislead under conversation leakage.** v1's val
   selector acc 0.871 / oracle 6.16 vs v2's 0.540 / 3.94 — yet v2 serves far better.
   Cause: slicing at every turn puts neighboring turns of the same conversation in
   train and val; v1's small 158-row split made the leak dominant (its val claimed
   0.87 top-1 agreement while the temp-0 arm measured ~0.52 true). Fix for future
   runs: split by conversation id, not by row.
3. **v2 data is end-to-end self-consistent**: one rendering path (our contexts →
   quant server → responses → merge_regen.py → prepare-data), vs v1's two subtly
   different renderings via the speculators dataset loader (tool-turn handling).

**Pipeline notes (v2).** Custom chat_template.jinja ships in the quant dir and is
what vLLM/prepare-data used all along; transformers 4.x cannot read standalone
chat_template.jinja files — the slicer length-check silently mis-rendered (fix:
render via 5.x tokenizer, tokenize=False + explicit encode). Regen client
resume-capable (regen_quant_all.py); merge (merge_regen.py) validated against
speculators' own boundary convention (usage.prompt_tokens == loss_mask flip).

**Next rung.** 20k+ fresh conversations from the 645k-conversation local pool
(build_cascade_slices.py stratified sampling, bigger N) — token multiple scales
properly there; big iron (offered) turns the ~3-week GB10 pipeline into ~1–2 days.
Also queued: conversation-id val split, reduced draft vocab head, block-16 sweep,
W8 of the drafter (precedent: lued/Qwen3.8-27B-DFlash2-W8, acceptance-neutral).

|---|---|---|---|---|

## Results — v3.5 recipe ablation (2025-10-11, same 29M tokens, paper recipe)

Hypothesis: v1→v3 scaling deceleration is partly undertraining — the DFlash paper's
recipe (block 16, lr 6e-4 cosine + 0.04 warmup, 6 epochs, gamma 7, 512 anchors) might
lift acceptance on the SAME data. Answer: **no — it hurts at our scale** (their recipe
is co-adapted with 800K-sample training sets).

| Config | Ladder metric (8-tok chain) | Per-pos p1 | recall@16 | selector acc |
|---|---|---|---|---|
| v3 (block 8, lr 1e-4, 3 ep) | **2.74** | 0.609 | **0.727** | 0.690 |
| v3.5 (block 16, paper recipe) serve-down | 2.38 | 0.535 | 0.615 | 0.710 |

v3.5 native block-16 (15 spec tokens, ceiling 16): acceptance 2.73, per-position
0.567/0.332/0.217/... — lower than v3 at every position. Teacher-forced selection
improved (0.710) while candidate coverage collapsed (recall@16 0.727 -> 0.615):
block-16 training spreads drafter capacity across more positions and dilutes
top-16 mass exactly where acceptance lives.

**But the serving story flips**: on identical 20 prompts / temp 1.0 / conc-8,
v3.5-b16 accepted throughput = **144.6 tok/s vs v3's 38.7** (3.7x) at equal
acceptance (2.73 vs 2.74) — one-forward 15-token drafting is that much cheaper
per accepted token. Block-16 is the deployment config regardless of ladder metric;
the ladder metric (8-token chain) and wall-clock throughput now diverge, and the
ablation rung should train block-16 natively and report both.

Mechanistic note: serve-down is NOT a truncation of native stats (pos-1 0.567 native
vs 0.535 served) — acceptance is trajectory-dependent; earlier rejections shift the
context distribution the drafter sees downstream.

**Implications for the ablation rung.** (1) Data remains the only lever that has ever
moved the ladder (1.53/2.18/2.74, all data-side; recipe causally ruled out at 29M).
Extrapolation ~3.0-3.3 at 150M stands. (2) Recipe x scale interaction is unresolved:
our conservative recipe won at 29M, theirs at 800K samples; at ablation scale run
both LRs (~$12/arm) — cheap against regen. (3) Add the 5th target tap (needs the
bigger-disk machine anyway). (4) Report accepted-token throughput alongside acceptance
from here on — it is the deployment metric.

## Prototype: fp8 hidden-state storage (validated on GB10, 2025-10-11 evening)

Question: can states live on disk as float8_e4m3fn (half the bytes) with training
parity? Method: 158-row v1 dataset twinned (bf16 vs fp8), identical 1-epoch
speculators runs (sdpa, lr 1e-4, seed defaults), paired step-loss + val comparison.

Results:
- Storage: exactly 0.5x (14.55 GB -> 7.28 GB). Fidelity: rel err 2.65% uniform,
  cos >= 0.9997 per tap.
- Training: 51/51 paired steps, mean loss delta +0.022 on losses spanning
  0.03-7.5, sign-mixed = noise. Val: recall@16 0.782 (bf16) vs 0.792 (fp8);
  selector acc 0.911 vs 0.898. Both within 158-row noise.
- Context: the trainer's default augmentation ALREADY adds +/-0.05 uniform noise
  to states (train/noise_transforms.py) — same order as fp8 dither. The pipeline
  is designed for this noise regime.

Required (1-line) patch: speculators/train/data.py _get_raw_data must cast
loaded hidden_states to hidden_states_dtype (bf16); otherwise raw fp8 reaches
the noise transform's rand_like and crashes. Saved: patches/speculators_fp8_load_cast.patch
(bf16 datasets unaffected). extract_batched.py now takes an "fp8" arg to store
e4m3 at save time.

Node plan updated: extraction saves fp8 -> 144k-row full-yield (~260M tok) states
drop 5.1 TiB -> ~2.5 TiB, fitting the 4TB node. Launch-day full A/B (2k rows,
30 min/arm on B200) remains the go/no-go gate; bf16 fallback costs only the hour.

## CORRECTION: 20-prompt ladder metrics convention (Oct 12)

Two errors found while evaluating v4a, both root-caused:

1. vLLM SpecDecoding metrics are PER-INTERVAL (~10s), not per-run. The old
   convention ("last line after prompts complete") is straggler-skewed for
   fast runs: v4a_b8's last interval held 178 tokens vs 3,264 in the first.
   All ladder numbers recomputed as sum(Accepted_i)/sum(Accepted_i/acc_len_i).
2. The recorded "v3.5 b16-native = 3.72" was a confabulation — the log
   contains exactly one SpecDecoding line: 2.73. (3.7x was the THROUGHPUT
   ratio at block 16, which is real: 144.6 vs 38.7 tok/s.)

Corrected ladder (20 held-out prompts, temp 1.0, 250 tok):
- v1 1.53 / v2 2.18 (single-interval runs, unchanged)
- v3 b8-native 2.74
- v3.5 b16-native 2.73, b8-serve-down 2.70 -> the "paper recipe -13% on
  acceptance" finding was a convention artifact; v3.5 ~= v3 on acceptance,
  its win was throughput (3.7x at b16).
- v4 arm A (lr 1e-4, 3ep, 260M tok): b16-native 3.14, b8-serve-down 3.18

v4a read: +0.4 over the 29M-token runs at both serving configs; the 9x data
rung moves acceptance materially, and the b16-trained drafter serves down to
7 spec tokens with no acceptance penalty. External anchors (speculator_

## Engineering learnings & postmortem (v1-v4 arc, consolidated Oct 12)

### speculators internals (learned the hard way)

1. TAP CONVENTION: `--target-layer-ids` lists the N AUX taps. States must be
   N+1 taps: aux layers + the FINAL layer (e.g. ids [2,10,17,24,29] on a
   32-layer model -> states [2,10,17,24,29,32]). The dataloader splits
   hs[:, :-1] -> aux input (len(ids) x hidden) and hs[:, -1] ->
   verifier_last stream. Validate states-vs-draft shapes BEFORE bulk
   extraction: draft aux dim = len(target_layer_ids) x hidden. The v4
   mis-extraction (5-tap states for a 5-aux draft) cost a full 2h re-extract
   + ~3.5h total slip.
2. TRAINER SAVE GATE: with checkpoint_freq=2, an ODD-epoch-count run never
   saves its final epoch ((epoch+1) % freq != 0 -> skip; epoch 0 always
   saves). Rule: freq=1, or even epoch counts. Arm A's final epoch was
   recovered by re-running with freq=1 — resume worked perfectly (exact
   global_step restart, fast-skip sampler slice, no recompute).
3. EPOCH SIZES VARY (sampler packing): 27k-33k steps/epoch on the same run.
   Never extrapolate ETA from a uniform-steps assumption; use measured
   epoch-boundary spans.
4. Extraction on quant (W4A16) via vLLM = corrupt states (v1 lesson, held):
   transformers-only forward for state extraction. fp8 state storage is
   sound: 0.5x disk, cos >= 0.9997 vs bf16, training parity gates passed
   (51/51 steps, mean loss delta +0.038, val straddles).

### performance

5. Solo state extraction is CPU-TAIL-BOUND: single-threaded
   bf16->fp8 cast + safetensors serialize + ~40MB/row NVMe write dominates
   the GPU forward on long rows (GPU duty ~50%, util dips to 2-5% are the
   write phase, NOT a stall). Fixes for next time (in order of value):
   fp8 cast on GPU before .cpu(), writer thread pool overlapping the next
   forward, fewer/larger files. Co-resident vLLM used to hide this; solo
   runs expose it.
6. PROGRESS PRINTS LIE NEAR COMPLETION: 2000-row-threshold prints make a
   finishing run look stalled (v4 re-extract "frozen" at 58k/72.5k while
   actually 95% done by tokens). Verify with DONE lines, file mtimes, and
   token-based math — rows/s on length-sorted data declines mechanically.

### operations

7. Early-check discipline: every failure in this arc (bad flag, shape
   mismatch, OOM, save gate) announced itself within 90s-4min of launch.
   Check at 90s and 4min; long sleeps before first check waste the exact
   window where failures are cheap to catch.
8. Never couple a remote script launch to an ssh command that can hit a
   tool timeout — the kill takes the script with it mid-health-loop while
   its nohup'd vllm child survives orphaned. Launch via setsid, return
   immediately, poll separately.
9. pkill footguns (three separate incidents): bracket trick for
   self-exclusion, never kill+launch in ONE command, and never pkill a
   pattern that matches another part of the same compound command line
   (launching "vllm serve" then pkill-ing "vllm serve" in one line
   self-terminates the shell, exit 143).
10. First dflash2 serve on a box stalls minutes in flashinfer JIT cubin
    downloads (network-bound, "Building JIT module topk") — cached in
    ~/.cache/flashinfer after; not a hang.
11. RunPod teardown protocol (validated): STOP preserves /root disk at
    storage-only billing; TERMINATE destroys. Before either: pull finals,
    per-epoch checkpoints (sha spot-check vs pod), conversation JSONLs
    (the truly irreplaceable data — states re-extract in ~3h GPU from
    them via the committed pipeline), and all logs. Optimizer states are
    optional (only exact-resume value).

### estimation postmortem (v4 rung)

Promised ~12:00 UTC at training launch; delivered ~15:30. Slips, honestly:
tap-convention bug +3.5h (should have validated shapes pre-extraction),
CPU-tail extraction +1h (known fix skipped), epoch-size assumption +45min
(unmeasured extrapolation), save-gate bug +1h (resume recovery). All four
were process errors, not compute necessities. The stable pattern: ETA from
MEASURED spans of the previous identical unit (epoch boundaries, chunk
extraction), not from first-principles rates.

### dead ends (do not retry)

- fp8 backbone-direct (`model.model(...)` to skip the wrapper): breaks the
  compressed_tensors quant lifecycle — quantized Linear exposes no .weight
  outside its wrapper. Use `model(..., logits_to_keep=1)`.
- MAX_BATCH_TOKENS 32768 for extraction OOMs when co-resident with vLLM at
  0.45 util; 16384 is the working value.
- Extractor self-comparison validation (ref == OUT on same file): 20min of
  CPU grind per chunk for zero information — skip when samefile.
- `--max-samples` is a prepare-data flag, not a train flag (no effect on
  training epochs/steps).
- Online no-disk training (rasyosef-style states-on-the-fly): unsafe on
  quant verifiers — states must come from transformers forward, which
  rules out the vLLM-in-the-loop online path.

## Scaling and epoch synthesis (v1→v4, fixed blend)

| rung | tokens | ladder τ (b16) |
|------|--------|----------------|
| v1   | 4.6M   | 1.53           |
| v3.5 | 29M    | 2.73           |
| v4 final | 260M | 3.25           |
| v4 champion | 260M, 2 ep | **3.44** |

6.3x tokens (4.6→29M) bought +1.2; 9x tokens (29→260M) bought +0.7 —
strongly diminishing, log-linear-ish, matching rasyosef's own 4M→100M
curve. Most of the 260M rung's value arrived in the first two epochs:

Epochs: peak acceptance ≠ end of training. armB (6e-4) peaks at ep 2 then
declines while val loss still improves; armA (1e-4) climbs monotonically
but ends lower — the peak is a high-LR phenomenon, and val loss is an
unreliable selector at high LR. Consequences already locked in: every new
arm trains 2-3 epochs at checkpoint-freq 1 with per-epoch ladder evals;
warm-start arms get a stronger prior (the champion peaked early — it had
not saturated; there is room above 3.44 without new data). The 27B-rung
projection follows this curve: 260M→~1B tokens extrapolates to roughly
+0.3–0.5 τ, which the v5 verdict will weigh against the ~68h+ pod cost of
a 27B-verifier rung.

### Per-lever attribution (ladder, interval-weighted, temp 1.0)

| arm | lever | ep1 | ep2 | vs champion |
|-----|-------|-----|-----|-------------|
| champion (v4 armB-ep2) | — | 3.443 | — | — |

## data blend: what's actually best (consolidated Oct 13, post-v5)

Question: what data blend makes the best drafter? Measured answer:

**The champion's own — chat-heavy cascade, 260M tok, fresh-trained 6e-4
cosine, stopped at epoch 2. Every deviation lost.**

| blend delta | method | result |
|---|---|---|
| chat-heavy cascade 260M (champion) | fresh, paper recipe | 3.443 |
| +100M more chat | warm-start 2e-4 | -0.28/-0.42 (arm E) |
| 80M math/swe/terminal tilt | warm-start 2e-4 | -0.16; math itself -0.23 (arm D) |

1. **You cannot improve the peaked champion by re-blending on top of it.**
   The math tilt didn't even lift math — null, not trade-off. No per-traffic
   routing story. The domain-split hypothesis (rasyosef) does not transfer
   via fine-tune.
2. **Recipe-vs-data confound**: arm E declined on MATCHED chat data, so
   much of the degradation is the 2e-4 warm-start on a peaked model, not
   the mix. Fresh-init on a different blend was never run (arm C cancelled
   on negative readouts) — cross-paper, a fresh math-heavy blend could
   still win on math. Known open cell.
3. **Blend is the weaker dial**: data SCALE moved +0.52 per 9x (29M->260M);
   STOPPING moved +0.19 (ep2 vs ep6). Blend moved <=0 through every
   fine-tune we ran. Budget priority follows.
